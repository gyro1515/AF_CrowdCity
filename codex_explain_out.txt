## 2. CharacterController 방식과의 차이

| 항목 | CharacterController.Move | 현재 SDF WallSolver |
|---|---|---|
| 충돌 형상 | 높이를 가진 3D capsule | XZ 평면의 점 + 반지름/skin 여유 거리 |
| 벽 정보 | 현재 PhysX collider/mesh | 미리 베이크한 float 거리 배열 |
| 이동 검사 | 캡슐 이동과 scene collider 충돌을 네이티브 물리에서 해결 | 이동을 최대 0.05m로 잘라 SDF를 조회 |
| 침투 해소 | overlap recovery/depenetration | gradient 방향으로 시작·끝 최대 4회 보정 |
| 벽 슬라이딩 | 충돌로 막힌 성분을 제한하고 collider 표면을 따라 이동 | 법선 방향 위치만 되밀어 접선 이동을 남김 |
| skin | CC의 `skinWidth=0.08` | `radius + skinWidth + 0.05m bias` |
| 처리 범위 | 경사, step, 높이, 동적 collider 등 3D CCT 기능 | 정적으로 베이크된 XZ 벽 footprint만 |
| 유닛 간 충돌 | 가능하지만 이 프로젝트에서는 Unit-Unit 충돌을 끔 | 처음부터 처리하지 않음 |

Unity 공식 문서로 확인되는 내용은 다음까지입니다.

- CharacterController는 capsule 형태입니다.
- `Move`에 넘긴 이동량은 충돌에 의해 제한됩니다.
- collider를 따라 미끄러지는 동작을 합니다.
- Skin Width는 약간의 관통을 허용해 지터와 끼임을 줄입니다.
- `enableOverlapRecovery`는 정적 물체와 겹친 CCT를 안전한 위치로 이동시키며 기본 활성입니다.
- Built-in 3D Physics는 Nvidia PhysX 기반입니다.

근거: [CharacterController 컴포넌트](https://docs.unity3d.com/kr/current/Manual/class-CharacterController.html), [Move API](https://docs.unity3d.com/kr/2022.3/ScriptReference/CharacterController.Move.html), [슬라이딩을 명시한 Unity Move 문서](https://docs.unity3d.com/kr/2019.3/ScriptReference/CharacterController.Move.html), [enableOverlapRecovery](https://docs.unity3d.com/kr/2022.2/ScriptReference/CharacterController-enableOverlapRecovery.html), [Unity Built-in Physics](https://docs.unity3d.com/kr/current/Manual/PhysicsSection.html).

중요한 한계가 있습니다. 저장소와 Unity 공개 API 문서에는 `CharacterController.Move`가 내부에서 캡슐 sweep을 정확히 몇 번, 어떤 순서로 수행하는지 공개되어 있지 않습니다. 로컬 코드도 이를 “PhysX capsule sweep 대체”라고 주석으로 표현할 뿐입니다([WallSolver.cs:5](D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Crowd/Core/WallSolver.cs:5)).

따라서 “캡슐을 이동 경로로 sweep하고, 겹침을 풀고, 접선 방향으로 슬라이드한다”는 것은 CCT를 이해하기 위한 일반적인 구현 모델이자 커밋의 주장입니다. 정확한 네이티브 sweep 횟수나 내부 처리 순서는 코드 미확인입니다.

또한 SDF는 완전한 CC 대체품이 아닙니다. XZ 전용이고 유닛 충돌을 처리하지 않는다는 계약이 코드에 명시되어 있습니다([WallSolver.cs:9](D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Crowd/Core/WallSolver.cs:9)). 움직이는 벽, 새로 생긴 collider, 계단·경사·높이에 따른 3D 충돌도 현재 SDF에는 반영되지 않습니다.

## 3. 왜 빨라지는가?

핵심은 복잡한 질문을 미리 계산해 두었다는 점입니다.

기존 CC 경로에서는 agent마다 `CharacterController.Move`로 네이티브 PhysX에 들어가 현재 scene collider들과의 충돌을 해결해야 합니다. 일반적인 물리 계산은 broad phase에서 후보 collider를 줄이고, narrow phase에서 실제 형상 충돌을 판단합니다([Unity broad phase 최적화 문서](https://docs.unity3d.com/Manual/physics-optimization-cpu-broad-phase.html)). 복잡한 MeshCollider가 많고 agent가 수백 명이면 이 호출이 agent 수만큼 반복됩니다.

SDF 경로는 도시의 40개 MeshCollider와 7,288개 삼각형을 에디터 베이크 때 처리해 거리 배열 하나로 바꿉니다. 런타임에는:

- 좌표를 grid index로 바꾸고
- float 네 개를 읽어 보간하고
- 필요하면 정해진 횟수만큼 gradient 보정합니다.

즉 매 agent 이동마다 collider 후보 검색과 삼각형 형상 판정을 다시 하지 않습니다. C#→네이티브 `CharacterController.Move` 호출도 사라집니다. 현재 SDF 구현이 Burst나 멀티스레드가 아닌데도 구조적으로 더 저렴할 수 있는 이유입니다.

다만 “결정적이라서 빠르다”는 설명은 틀립니다. 결정성과 성능은 직접적인 인과관계가 아닙니다.

이 구현은 “불변의 베이크 배열 + 고정 순서 + 제한된 반복 계산”을 선택했기 때문에:

- 같은 입력에서 재현하기 쉬운 결정적 벽 해소
- 저렴한 런타임 계산

두 장점을 함께 얻은 것입니다. 전체 게임의 플랫폼 간 bit-exact 결정성까지 검증된 것은 아니며, 아래의 PhysX 쿼리도 여전히 남아 있습니다.

## 4. 초보자용 비유

첫 번째 비유는 “매번 부딪혀 보기”와 “거리 지도 보기”입니다.

- CC.Move: 매 프레임 사람 모양 캡슐을 실제 도시 안으로 밀어 보면서 “어느 벽과 부딪혔지?”, “얼마나 되돌려야 하지?”, “어느 방향으로 미끄러져야 하지?”를 물리엔진에 묻습니다.
- SDF: 도시 전체에 “여기서 가장 가까운 벽까지 몇 m인가?”가 적힌 지도를 미리 만들어 둡니다. 캐릭터는 현재 칸의 숫자를 보고 너무 가까우면 지도에 표시된 바깥 방향으로 조금 이동합니다.

두 번째 비유는 내비게이션과 현장 측량입니다.

- CC는 이동할 때마다 현장에 측량팀을 보내 실제 건물 모양을 확인하는 방식입니다.
- SDF는 측량을 한 번 끝내고 거리 지도를 배포한 뒤, 모든 사람이 자기 좌표의 숫자만 읽는 방식입니다.

## 2. CharacterController 방식과의 차이

| 항목 | CharacterController.Move | 현재 SDF WallSolver |
|---|---|---|
| 충돌 형상 | 높이를 가진 3D capsule | XZ 평면의 점 + 반지름/skin 여유 거리 |
| 벽 정보 | 현재 PhysX collider/mesh | 미리 베이크한 float 거리 배열 |
| 이동 검사 | 캡슐 이동과 scene collider 충돌을 네이티브 물리에서 해결 | 이동을 최대 0.05m로 잘라 SDF를 조회 |
| 침투 해소 | overlap recovery/depenetration | gradient 방향으로 시작·끝 최대 4회 보정 |
| 벽 슬라이딩 | 충돌로 막힌 성분을 제한하고 collider 표면을 따라 이동 | 법선 방향 위치만 되밀어 접선 이동을 남김 |
| skin | CC의 `skinWidth=0.08` | `radius + skinWidth + 0.05m bias` |
| 처리 범위 | 경사, step, 높이, 동적 collider 등 3D CCT 기능 | 정적으로 베이크된 XZ 벽 footprint만 |
| 유닛 간 충돌 | 가능하지만 이 프로젝트에서는 Unit-Unit 충돌을 끔 | 처음부터 처리하지 않음 |

Unity 공식 문서로 확인되는 내용은 다음까지입니다.

- CharacterController는 capsule 형태입니다.
- `Move`에 넘긴 이동량은 충돌에 의해 제한됩니다.
- collider를 따라 미끄러지는 동작을 합니다.
- Skin Width는 약간의 관통을 허용해 지터와 끼임을 줄입니다.
- `enableOverlapRecovery`는 정적 물체와 겹친 CCT를 안전한 위치로 이동시키며 기본 활성입니다.
- Built-in 3D Physics는 Nvidia PhysX 기반입니다.

근거: [CharacterController 컴포넌트](https://docs.unity3d.com/kr/current/Manual/class-CharacterController.html), [Move API](https://docs.unity3d.com/kr/2022.3/ScriptReference/CharacterController.Move.html), [슬라이딩을 명시한 Unity Move 문서](https://docs.unity3d.com/kr/2019.3/ScriptReference/CharacterController.Move.html), [enableOverlapRecovery](https://docs.unity3d.com/kr/2022.2/ScriptReference/CharacterController-enableOverlapRecovery.html), [Unity Built-in Physics](https://docs.unity3d.com/kr/current/Manual/PhysicsSection.html).

중요한 한계가 있습니다. 저장소와 Unity 공개 API 문서에는 `CharacterController.Move`가 내부에서 캡슐 sweep을 정확히 몇 번, 어떤 순서로 수행하는지 공개되어 있지 않습니다. 로컬 코드도 이를 “PhysX capsule sweep 대체”라고 주석으로 표현할 뿐입니다([WallSolver.cs:5](D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Crowd/Core/WallSolver.cs:5)).

따라서 “캡슐을 이동 경로로 sweep하고, 겹침을 풀고, 접선 방향으로 슬라이드한다”는 것은 CCT를 이해하기 위한 일반적인 구현 모델이자 커밋의 주장입니다. 정확한 네이티브 sweep 횟수나 내부 처리 순서는 코드 미확인입니다.

또한 SDF는 완전한 CC 대체품이 아닙니다. XZ 전용이고 유닛 충돌을 처리하지 않는다는 계약이 코드에 명시되어 있습니다([WallSolver.cs:9](D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Crowd/Core/WallSolver.cs:9)). 움직이는 벽, 새로 생긴 collider, 계단·경사·높이에 따른 3D 충돌도 현재 SDF에는 반영되지 않습니다.

## 3. 왜 빨라지는가?

핵심은 복잡한 질문을 미리 계산해 두었다는 점입니다.

기존 CC 경로에서는 agent마다 `CharacterController.Move`로 네이티브 PhysX에 들어가 현재 scene collider들과의 충돌을 해결해야 합니다. 일반적인 물리 계산은 broad phase에서 후보 collider를 줄이고, narrow phase에서 실제 형상 충돌을 판단합니다([Unity broad phase 최적화 문서](https://docs.unity3d.com/Manual/physics-optimization-cpu-broad-phase.html)). 복잡한 MeshCollider가 많고 agent가 수백 명이면 이 호출이 agent 수만큼 반복됩니다.

SDF 경로는 도시의 40개 MeshCollider와 7,288개 삼각형을 에디터 베이크 때 처리해 거리 배열 하나로 바꿉니다. 런타임에는:

- 좌표를 grid index로 바꾸고
- float 네 개를 읽어 보간하고
- 필요하면 정해진 횟수만큼 gradient 보정합니다.

즉 매 agent 이동마다 collider 후보 검색과 삼각형 형상 판정을 다시 하지 않습니다. C#→네이티브 `CharacterController.Move` 호출도 사라집니다. 현재 SDF 구현이 Burst나 멀티스레드가 아닌데도 구조적으로 더 저렴할 수 있는 이유입니다.

다만 “결정적이라서 빠르다”는 설명은 틀립니다. 결정성과 성능은 직접적인 인과관계가 아닙니다.

이 구현은 “불변의 베이크 배열 + 고정 순서 + 제한된 반복 계산”을 선택했기 때문에:

- 같은 입력에서 재현하기 쉬운 결정적 벽 해소
- 저렴한 런타임 계산

두 장점을 함께 얻은 것입니다. 전체 게임의 플랫폼 간 bit-exact 결정성까지 검증된 것은 아니며, 아래의 PhysX 쿼리도 여전히 남아 있습니다.

## 4. 초보자용 비유

첫 번째 비유는 “매번 부딪혀 보기”와 “거리 지도 보기”입니다.

- CC.Move: 매 프레임 사람 모양 캡슐을 실제 도시 안으로 밀어 보면서 “어느 벽과 부딪혔지?”, “얼마나 되돌려야 하지?”, “어느 방향으로 미끄러져야 하지?”를 물리엔진에 묻습니다.
- SDF: 도시 전체에 “여기서 가장 가까운 벽까지 몇 m인가?”가 적힌 지도를 미리 만들어 둡니다. 캐릭터는 현재 칸의 숫자를 보고 너무 가까우면 지도에 표시된 바깥 방향으로 조금 이동합니다.

두 번째 비유는 내비게이션과 현장 측량입니다.

- CC는 이동할 때마다 현장에 측량팀을 보내 실제 건물 모양을 확인하는 방식입니다.
- SDF는 측량을 한 번 끝내고 거리 지도를 배포한 뒤, 모든 사람이 자기 좌표의 숫자만 읽는 방식입니다.

## 검증 및 변경 보고

- 변경된 파일: 없음. 읽기 전용 조사만 수행했습니다.
- 기존 소유권: `CrowdRoot`가 agent 이동과 세션 수명의 `WallField`를 소유하며, `GameplayRoot`가 직접 tick을 호출합니다. 새 API·상태·통신 방식은 추가하지 않았습니다.
- 확인 방법: 브랜치/커밋 이력, 전체 호출부 검색, prefab 직렬화 값, SDF payload 크기와 에셋 메타를 교차검증했습니다.
- Unity Editor/PlayMode와 실제 Profiler 측정은 실행하지 않았습니다.
- 코드 주석의 “기본 OFF”와 실제 프리팹 ON이 충돌하므로, 요청대로 실제 직렬화 값을 우선했습니다.

## 핵심 3줄 요약

1. 현재 실제 게임 프리팹은 SDF ON이며, SDF 로드 실패나 스위치 OFF일 때만 `CharacterController.Move`로 폴백합니다.
2. SDF는 매 agent의 PhysX 충돌 계산 대신 미리 만든 2D 벽 거리 지도를 조회하고 gradient로 위치를 보정하므로 구조적으로 훨씬 저렴합니다.
3. spawn·중립·라이벌 Raycast 등 물리는 여전히 남아 있고, 94%·12.3배·3.9mm·1.1% 같은 수치는 추적된 프로파일 결과로 재확인되지 않았습니다.
