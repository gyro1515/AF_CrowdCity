역할: 너는 **Unity 시니어 게임 프로그래머**다. AF_CrowdCity의 crowd 시뮬레이션 CPU 병목(확정: GameplayRoot.Update → CrowdRoot.SimTick, 사용자 Profiler 실측으로 GameplayRoot.Update가 주원인 확인)을 **최소 변경으로 최적화하는 상세 구현 설계 + Decision Log**를 작성하라. 이것은 Claude 에이전트와의 교차검증 중 한 축이며, 별도로 동일 과제를 Claude가 독립 설계한다. 이후 두 설계를 대조해 합의점에 도달시킬 것이므로, **대조 가능하도록 아래 결과물 스펙을 정확히 따르라**.

배경(확정 사실):
- 라이브 프리팹 `_useSdfSolver:1`(SDF ON, CC.Move는 폴백 전용). Human에 per-frame Update 없음. gpuSkinning ON(스키닝 GPU). 즉 데스크톱 2000 병목은 렌더가 아니라 **sim(script)**.
- 유력 주범(코드 근거 기반 가설, 미실측): combat/recruit의 SpatialGrid 이웃 쿼리가 밀도에 초선형(CombatResolver.cs QueryCircle per non-neutral+per leader, RecruitResolver.cs per neutral), victim 정렬 O(v²)(CombatResolver.cs SortVictims). 800→2000 고정맵 = 개체2.5×+밀도2.5×.
- Crowd/Core는 순수 C#, 이미 SoA(AgentBuffer=managed 배열), WallSolver/SDF는 NativeArray·float2/math(Burst-shaped). Core asmdef이 이미 Burst/Collections/Mathematics 참조, allowUnsafeCode=false. 잔존 Physics: 중립 wander Raycast, spawn CheckSphere. 단일 System.Random.
- **제약: 사용자의 현재 구조 리팩토링이 Crowd/Core + CrowdRoot를 전부 건드린다.** 따라서 이 설계는 "리팩토링 완료 후 rebase해서 적용"할 목표 end-state 설계여야 하며, 특정 라인 번호에 못박지 말고 컴포넌트/책임 단위로 기술하라(현재 라인은 근거 인용용으로만).
- 결정성 계약: 로컬(same-build) 재현만(DESIGN.md), cross-ISA/멀티/리플레이 없음(싱글플레이). 오라클은 same-seed 2× byte 비교.

목표: SimTick CPU 비용을 2000에서 대폭↓, 나아가 수만까지 확장 가능한 sim 구조. 거동/결정성 보존.

결과물 스펙(이 순서·이 제목으로):
## 1. Decision Log (CLAUDE.md §1, 5줄: 소유자 / 파일위치 / 상태위치 / 통신방법 / 영향파일)
## 2. Target end-state (sim 커널 구조)
- NativeArray SoA 레이아웃(어떤 필드가 어떤 컨테이너로), 어떤 단계가 IJobParallelFor로 가고 어떤 단계가 직렬로 남는가, 데이터 소유는 CrowdRoot가 갖는가, Persistent/Dispose 책임.
## 3. 순서화된 마일스톤 (각각: 변경 스코프 + 검증 게이트)
- M-sim-0 헤드리스 배치 2000/5000+ 단계별 프로파일(병목 sub-stage 실측 — grid/recruit/combat/steering 중 무엇인지 확정)
- M-sim-1 grid 쿼리 밀도 캡핑(초선형 항 제거) — 알고리즘 설계 포함
- M-sim-2 NativeArray SoA + Burst + IJobParallelFor 이식·병렬화
- M-sim-3 잔존 Physics.Raycast→SDF 질의 대체 + baked CC 제거
## 4. 결정성 계획
- FloatMode/FloatPrecision, RNG per-agent 스트림 설계(현 단일 System.Random 대체), grid/recruit/combat canonical order, 오라클 재기준선 절차, worker수/batch permutation 불변 테스트.
## 5. 밀도 캡핑 알고리즘 설계
- 이웃 쿼리 작업량을 어떻게 bound하나(k-nearest? 셀당 상한? 반경 예산?), 게임플레이 의미(접촉 즉시 판정 등) 훼손 최소화 방안, 캡 파라미터, 거동 게이트.
## 6. 검증 방법론
- 하네스 확장(2000+), 오라클 재기준선, 성능 게이트 정의, 거동 A/B, GC/무할당 확인.
## 7. 리스크 + rebase 노트 (리팩토링이 Crowd/Core+CrowdRoot 전부 건드림)
## 8. 합의 후보 (다른 설계자와 맞출 핵심 설계 결정 5~8개)

주의: Burst+멀티스레드는 상수배 이득, 초선형 항은 알고리즘 수정이 더 근본적임을 우선순위에 반영하라. 성능 수치는 실측 부재이므로 "외삽" 명시. 추측 금지, 확인 불가는 명시. rg로 필요한 코드만 재확인. 소스 덤프 금지, 설계와 근거만.
