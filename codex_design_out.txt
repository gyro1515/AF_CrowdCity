## [권장 접근법+근거]

권장안은 **기존 GameObject/CharacterController 경계를 유지한 Jobs + Burst + Persistent NativeArray SoA 하이브리드**다.

핵심은 DOTS 전환이 아니라 다음 경계를 명확히 나누는 것이다.

```text
직전 tick 스냅샷
  → Burst 계산 커널
  → main-thread CharacterController/Physics 적용
  → 실제 위치 NativeArray 반영

  → main-thread 순차 commit
  → 기존 순서로 이벤트 발행
```

이유는 다음과 같다.

- [AgentBuffer.cs](D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Crowd/Core/AgentBuffer.cs:19)는 이미 `Id/Team/IsLeader/Pos/Scale`별 managed SoA다. 따라서 단순한 AoS→SoA 변환이 아니라, Unity 오브젝트 접근 분리와 `NativeArray`/Burst 커널화가 실제 개선점이다.

## [데이터 레이아웃]

### 1. Persistent Native SoA

CrowdRoot가 다음 배열의 lifetime을 소유하고 `Initialize → Dispose/OnDestroy`로 관리한다.

```text
NativeArray<int>    Id
NativeArray<int>    Team
NativeArray<byte>   Flags          // leader, active 등
NativeArray<float2> Position
NativeArray<float>  Scale
NativeArray<float2> Velocity
NativeArray<float>  WanderHeading
NativeArray<float>  WanderTimer
NativeArray<float2> VisualPrev
NativeArray<float2> VisualCur
```

- agent index는 lifetime 동안 안정적으로 유지한다.
- capacity만큼 `Allocator.Persistent`로 한 번 할당한다.
- tick 안에서는 resize, `new List`, LINQ, boxing을 금지한다.
- Unity 오브젝트는 `Transform[]`, `CharacterController[]`, `Human[]` bridge 배열로만 남긴다.
- hot kernel은 Unity 오브젝트 배열을 전혀 참조하지 않는다.

초기에는 기존 `AgentBuffer`와 Native SoA를 나란히 유지해 golden 검증한다. 검증 후 Native SoA를 단일 source of truth로 승격한다.

### 2. follower 목록

팀별 follower 순서 자체가 동작 계약이므로 무작정 agent-index 순으로 재정렬하면 안 된다.

권장 구조는 팀별 fixed-capacity contiguous slab과 다음 보조 배열이다.

```text
FollowerIndices[team * capacity + slot]
FollowerCount[team]
FollowerSlotByAgent[agent]
```

이 구조에서 기존 `List`의 append와 swap-remove를 정확히 재현하면서 제거를 O(1)로 만들 수 있다. elimination의 “index 0 제거 후 swap” 순서 역시 그대로 모사해야 한다.

### 3. Flattened cell grid

현재 hash-linked grid를 다음 CSR형 구조로 바꾼다.

```text
CellCounts[cell]
CellOffsets[cell + 1]
CellWriteCursor[cell]
AgentIndices[agentCount]
```

Rebuild는 `count → prefix sum → fill`의 O(N+C) 선형 접근이다. query는 각 cell의 연속된 `AgentIndices` 범위만 돈다.

단, 기존 반환 순서를 반드시 재현해야 한다.

```text
cellY 오름차순
→ cellX 오름차순
→ 같은 cell 안에서는 agent index 내림차순
```

현재 head-prepend 때문에 같은 cell은 내림차순이다. separation float 합산 순서가 바뀌면 위치 snapshot도 달라질 수 있다.

후보를 `List<int>`에 담지 말고 커널이 cell range를 직접 순회하도록 한다.

## [커널·멀티스레드]

Burst 대상과 메인 스레드 대상을 구분한다.

| 단계 | 실행 방식 | 이유 |
|---|---|---|
| Grid count/prefix/fill | 우선 단일 `IJob` | 동일 cell 순서 보존 |
| Follower desired velocity/separation | `IJobParallelFor` 가능 | agent별 독립 output |
| Neutral 기본 이동 벡터 | 병렬 가능 | RNG 만료 처리 제외 |
| Recruit claimant 계산 | 병렬 가능 | neutral별 독립 slot |
| Recruit 결과 compact | 단일 `IJob` | neutral index 순서 유지 |
| Combat nearest/agent-local 계산 | 병렬 가능 | agent별 고정 output |
| Pair reduction/accumulator | 단일 `IJob` | 고정 pair 순서 필요 |
| Conversion/victim emit | 단일 `IJob` | 결과 발행 순서 필요 |
| RNG/Physics/CC.Move | 메인 스레드 직렬 | 호출·소비 순서 계약 |
| Commit/event publish | 메인 스레드 직렬 | 관찰 가능한 순서 계약 |

`IJobParallelFor`에서는 각 index가 자신의 output slot만 써야 한다. 다음은 금지한다.

- `NativeList.ParallelWriter`로 conversion/recruit 순서 없이 append
- atomic grid insert
- 공유 RNG
- `NativeParallelHashMap` 열거 순서 의존
- float atomic/reduction
- worker에서 EventBus publish

병렬 결과는 agent별 고정 slot에 쓴 뒤 단일 job이 agent/team 오름차순으로 compact한다.

또한 job을 잘게 쪼개 즉시 `Schedule().Complete()`하면 scheduling 비용이 이득을 상쇄할 수 있다. 가능한 한 커널을 fusion하고, 직렬 Burst 단계는 작은 N에서 `IJob.Run()`과 schedule을 모두 계측해 선택한다.

중요한 스냅샷 경계도 유지해야 한다.

- follower/AI steering은 직전 tick 말의 grid를 읽는다.
- 모든 movement가 끝난 뒤 grid를 rebuild한다.
- Recruit와 Combat은 동일한 이동 후/pre-commit snapshot을 읽는다.
- 같은 tick에 recruit된 neutral은 같은 tick combat에 참여하지 않는다.

float는 허용오차가 아니라 `SingleToInt32Bits`로 비교하고 전체 hash와 최초 불일치 필드를 출력한다.

### Burst float

`[BurstCompile(FloatMode = FloatMode.Strict, FloatPrecision = FloatPrecision.Standard)]`에서 시작하고 fast math는 금지한다. 기존 괄호와 합산 순서도 유지한다.

다만 Strict도 다음을 보장하지 않는다.

- x64 Editor와 ARM64 Android 간 bitwise 동일성
- Mono와 IL2CPP 간 동일성
- `Mathf`를 `math.*`로 바꾼 경우의 초월함수 동일성
- PhysX/CharacterController의 플랫폼 간 동일성

따라서 계약은 우선 “동일 Unity/Burst 버전, 동일 target architecture에서 리팩터 전후 bit-exact”로 정의해야 한다. Android와 Editor 사이까지 bit-exact가 필수라면 고정소수점/정수 시뮬레이션이 필요하며, 이는 현재 동작 동일성 범위를 넘어선다.

## [성능 측정법]

`-batchmode -nographics`에서 `Stopwatch.GetTimestamp()`를 이용한 ms/tick 측정은 가능하다. 단 Editor batchmode가 게임 플레이를 자동 실행해 주는 것은 아니므로 전용 runner가 필요하다.

권장 실행 형태:

```text
Unity.exe -batchmode -nographics
-projectPath <project>
-executeMethod CrowdPerformanceBatch.Run
-crowdCounts 100,300,500,800,1000,1200
-warmupTicks 300
-measureTicks 2000
-repetitions 5
-output <json>
-quit
```

측정 조건:

- 실제 config asset을 수정하지 않고 `GameConfigSO`를 메모리 clone한다.
- 코드 기본값은 800이지만 현재 `GameConfig.asset` 값은 310이므로 CLI override를 사용한다.
- spawn, domain load, 최초 Burst compile은 측정에서 제외한다.
- 200~500 warmup tick 후 2,000 tick을 측정한다.
- 매 tick timestamp만 배열에 기록하고 JSON/log는 종료 후 한 번만 출력한다.
- 동일 seed와 input trace로 이전/변경 commit을 각각 5회 측정한다.
- `mean/median/p95/p99/max ms/tick`, ticks/s, agent-ticks/s, GC alloc/tick을 기록한다.
- total SimTick 외에 restore, movement, mirror, grid, recruit, combat, commit, publish, render 단계를 분리한다.
- full evolving simulation과 동일 snapshot을 반복하는 kernel microbenchmark를 모두 둔다.

60fps 추정은 fixed simulation이 50Hz라는 점을 반영한다.

```text
필수 tick 조건:
T_tick_p95 < 20ms

평균 60fps 조건:
B_other_mean + (50 / 60) × T_tick_mean < 16.667ms

보수적 tail 조건:
B_other_p99 + T_tick_p99 < 16.667ms
```

한 프레임에 2~4 tick이 몰리는 backlog 프레임 빈도도 별도로 기록해야 한다.

Batchmode 결과는 회귀 추세용이다. 최종 최대 neutralCount는 약한 Android IL2CPP 실기기에서:

1. 100명 간격으로 통과 구간 bracket
2. 25~50명 단위 binary search
3. 5~10분 thermal steady-state
4. 3회 반복 중 가장 낮은 통과 count 채택

으로 정한다. 비용이 밀도에 따라 비선형이므로 먼 구간을 단일 선형식으로 외삽해서는 안 된다.

## [데이터 레이아웃]

### 1. Persistent Native SoA

CrowdRoot가 다음 배열의 lifetime을 소유하고 `Initialize → Dispose/OnDestroy`로 관리한다.

```text
NativeArray<int>    Id
NativeArray<int>    Team
NativeArray<byte>   Flags          // leader, active 등
NativeArray<float2> Position
NativeArray<float>  Scale
NativeArray<float2> Velocity
NativeArray<float>  WanderHeading
NativeArray<float>  WanderTimer
NativeArray<float2> VisualPrev
NativeArray<float2> VisualCur
```

- agent index는 lifetime 동안 안정적으로 유지한다.
- capacity만큼 `Allocator.Persistent`로 한 번 할당한다.
- tick 안에서는 resize, `new List`, LINQ, boxing을 금지한다.
- Unity 오브젝트는 `Transform[]`, `CharacterController[]`, `Human[]` bridge 배열로만 남긴다.
- hot kernel은 Unity 오브젝트 배열을 전혀 참조하지 않는다.

초기에는 기존 `AgentBuffer`와 Native SoA를 나란히 유지해 golden 검증한다. 검증 후 Native SoA를 단일 source of truth로 승격한다.

### 2. follower 목록

팀별 follower 순서 자체가 동작 계약이므로 무작정 agent-index 순으로 재정렬하면 안 된다.

권장 구조는 팀별 fixed-capacity contiguous slab과 다음 보조 배열이다.

```text
FollowerIndices[team * capacity + slot]
FollowerCount[team]
FollowerSlotByAgent[agent]
```

이 구조에서 기존 `List`의 append와 swap-remove를 정확히 재현하면서 제거를 O(1)로 만들 수 있다. elimination의 “index 0 제거 후 swap” 순서 역시 그대로 모사해야 한다.

### 3. Flattened cell grid

현재 hash-linked grid를 다음 CSR형 구조로 바꾼다.

```text
CellCounts[cell]
CellOffsets[cell + 1]
CellWriteCursor[cell]
AgentIndices[agentCount]
```

Rebuild는 `count → prefix sum → fill`의 O(N+C) 선형 접근이다. query는 각 cell의 연속된 `AgentIndices` 범위만 돈다.

단, 기존 반환 순서를 반드시 재현해야 한다.

```text
cellY 오름차순
→ cellX 오름차순
→ 같은 cell 안에서는 agent index 내림차순
```

현재 head-prepend 때문에 같은 cell은 내림차순이다. separation float 합산 순서가 바뀌면 위치 snapshot도 달라질 수 있다.

후보를 `List<int>`에 담지 말고 커널이 cell range를 직접 순회하도록 한다.

## [커널·멀티스레드]

Burst 대상과 메인 스레드 대상을 구분한다.

| 단계 | 실행 방식 | 이유 |
|---|---|---|
| Grid count/prefix/fill | 우선 단일 `IJob` | 동일 cell 순서 보존 |
| Follower desired velocity/separation | `IJobParallelFor` 가능 | agent별 독립 output |
| Neutral 기본 이동 벡터 | 병렬 가능 | RNG 만료 처리 제외 |
| Recruit claimant 계산 | 병렬 가능 | neutral별 독립 slot |
| Recruit 결과 compact | 단일 `IJob` | neutral index 순서 유지 |
| Combat nearest/agent-local 계산 | 병렬 가능 | agent별 고정 output |
| Pair reduction/accumulator | 단일 `IJob` | 고정 pair 순서 필요 |
| Conversion/victim emit | 단일 `IJob` | 결과 발행 순서 필요 |
| RNG/Physics/CC.Move | 메인 스레드 직렬 | 호출·소비 순서 계약 |
| Commit/event publish | 메인 스레드 직렬 | 관찰 가능한 순서 계약 |

`IJobParallelFor`에서는 각 index가 자신의 output slot만 써야 한다. 다음은 금지한다.

- `NativeList.ParallelWriter`로 conversion/recruit 순서 없이 append
- atomic grid insert
- 공유 RNG
- `NativeParallelHashMap` 열거 순서 의존
- float atomic/reduction
- worker에서 EventBus publish

병렬 결과는 agent별 고정 slot에 쓴 뒤 단일 job이 agent/team 오름차순으로 compact한다.

또한 job을 잘게 쪼개 즉시 `Schedule().Complete()`하면 scheduling 비용이 이득을 상쇄할 수 있다. 가능한 한 커널을 fusion하고, 직렬 Burst 단계는 작은 N에서 `IJob.Run()`과 schedule을 모두 계측해 선택한다.

중요한 스냅샷 경계도 유지해야 한다.

- follower/AI steering은 직전 tick 말의 grid를 읽는다.
- 모든 movement가 끝난 뒤 grid를 rebuild한다.
- Recruit와 Combat은 동일한 이동 후/pre-commit snapshot을 읽는다.
- 같은 tick에 recruit된 neutral은 같은 tick combat에 참여하지 않는다.

- count event team 오름차순.
- elimination event player 우선→rival team 오름차순.

### Golden trace

동일 seed, config clone, heading input trace, `dt=0.02`로 `{0, 300, 500, 800}` 및 복수 seed를 실행한다. 매 tick 다음을 기록한다.

- `id/team/isLeader/position/scale`
- velocity, wander heading/timer
- combat accumulator
- ordered recruit/conversion/elimination 결과
- `RejectionRate`, total/rejected/skipped/placed
- RNG draw 종류·순번·raw bits
- `CheckSphere`/Raycast 입력과 결과
- `CharacterController.Move` 입력과 실제 위치
- 이벤트 `(tick, sequence, type, team, payload)`

float는 허용오차가 아니라 `SingleToInt32Bits`로 비교하고 전체 hash와 최초 불일치 필드를 출력한다.

### Burst float

`[BurstCompile(FloatMode = FloatMode.Strict, FloatPrecision = FloatPrecision.Standard)]`에서 시작하고 fast math는 금지한다. 기존 괄호와 합산 순서도 유지한다.

다만 Strict도 다음을 보장하지 않는다.

- x64 Editor와 ARM64 Android 간 bitwise 동일성
- Mono와 IL2CPP 간 동일성
- `Mathf`를 `math.*`로 바꾼 경우의 초월함수 동일성
- PhysX/CharacterController의 플랫폼 간 동일성

따라서 계약은 우선 “동일 Unity/Burst 버전, 동일 target architecture에서 리팩터 전후 bit-exact”로 정의해야 한다. Android와 Editor 사이까지 bit-exact가 필수라면 고정소수점/정수 시뮬레이션이 필요하며, 이는 현재 동작 동일성 범위를 넘어선다.

-warmupTicks 300
-measureTicks 2000
-repetitions 5
-output <json>
-quit
```

측정 조건:

- 실제 config asset을 수정하지 않고 `GameConfigSO`를 메모리 clone한다.
- 코드 기본값은 800이지만 현재 `GameConfig.asset` 값은 310이므로 CLI override를 사용한다.
- spawn, domain load, 최초 Burst compile은 측정에서 제외한다.
- 200~500 warmup tick 후 2,000 tick을 측정한다.
- 매 tick timestamp만 배열에 기록하고 JSON/log는 종료 후 한 번만 출력한다.
- 동일 seed와 input trace로 이전/변경 commit을 각각 5회 측정한다.
- `mean/median/p95/p99/max ms/tick`, ticks/s, agent-ticks/s, GC alloc/tick을 기록한다.
- total SimTick 외에 restore, movement, mirror, grid, recruit, combat, commit, publish, render 단계를 분리한다.
- full evolving simulation과 동일 snapshot을 반복하는 kernel microbenchmark를 모두 둔다.

60fps 추정은 fixed simulation이 50Hz라는 점을 반영한다.

```text
필수 tick 조건:
T_tick_p95 < 20ms

평균 60fps 조건:
B_other_mean + (50 / 60) × T_tick_mean < 16.667ms

보수적 tail 조건:
B_other_p99 + T_tick_p99 < 16.667ms
```

한 프레임에 2~4 tick이 몰리는 backlog 프레임 빈도도 별도로 기록해야 한다.

Batchmode 결과는 회귀 추세용이다. 최종 최대 neutralCount는 약한 Android IL2CPP 실기기에서:

1. 100명 간격으로 통과 구간 bracket
2. 25~50명 단위 binary search
3. 5~10분 thermal steady-state
4. 3회 반복 중 가장 낮은 통과 count 채택

으로 정한다. 비용이 밀도에 따라 비선형이므로 먼 구간을 단일 선형식으로 외삽해서는 안 된다.

## [구현 단계]

1. 기준선과 계측 구축

- 기존 EditMode: Combat 26, Recruit 6, Grid/Steering 3, MatchRules 8.
- full-tick golden, RNG, Physics, event transcript 추가.
- phase Stopwatch와 Android ProfilerMarker 추가.
- 게이트: 동일 입력 3회 trace bit-exact, GC/tick 확인.

2. 할당과 capacity 정리

- resolver scratch, follower list, Rival AI query capacity를 agent capacity 기준으로 선할당.
- 새로운 동적 resize가 없도록 한다.
- 게이트: 모든 golden 동일, steady-state GC 0 B/tick.

3. Native SoA mirror 도입

- 기존 managed 경로를 유지하면서 NativeArray에 동일 데이터를 기록.
- 우선 직렬 managed kernel로 결과 비교.
- 게이트: 모든 필드 raw-bit 동일.

4. Flattened grid 도입

- 단일-thread rebuild/query부터 구현.
- 기존 cell/agent 순서를 그대로 재현.
- brute-force query와 기존 grid 양쪽 결과 비교.
- 게이트: query 순서와 full simulation trace 동일.

5. Recruit/Combat 단일-thread Burst화

- fixed-capacity 결과 buffer 사용.
- 기존 resolver와 dual-run 비교.
- 게이트: 26/26·6/6 및 ordered outcomes bit-exact.

6. Steering precompute 병렬화

- follower별 snapshot 계산만 `IJobParallelFor`.
- RNG, Physics, `CharacterController.Move`, Transform clamp는 메인 스레드 기존 순서.
- 게이트: Move 입력/출력과 full-tick trace 동일.

7. 제한적 Combat 병렬화

- agent-local nearest/assignment만 병렬화.
- pair reduction, accumulator, victim sort, emit은 직렬 유지.
- 결과는 agent index 기준으로 compact.
- 게이트: worker count/batch size를 바꿔도 동일 hash.

8. commit 구조 최적화

- follower slot map으로 기존 swap-remove/append 순서를 정확히 모사.
- 게이트: mass conversion/elimination 전용 golden 추가.

9. Android IL2CPP 검증

- Burst AOT 활성 확인.
- Persistent NativeArray leak 검사.
- 낮은 사양 ARM64 실기기에서 thermal benchmark.
- bit mismatch가 생긴 단계는 성능과 무관하게 롤백한다.

## [리스크]

- 실제 99% 안에서 `CharacterController.Move`, Transform/Animator 경계가 대부분이면 Burst 수학 커널만으로 얻을 수 있는 개선에는 상한이 있다.
- render interpolation이 CharacterController root Transform을 움직였다가 다음 tick에 복원하는 구조는 PhysX transform/broadphase 비용을 만들 가능성이 높다. phase 계측 없이 단정하면 안 된다.
- CSR grid가 현재 열거 순서를 조금이라도 바꾸면 separation float 합산과 snapshot이 달라진다.
- 작은 job의 schedule/complete 비용이 계산 이득보다 클 수 있다.
- Burst Strict는 플랫폼 간 bitwise 결정론을 보장하지 않는다.
- victim insertion sort를 O(v log v)로 바꿀 경우 완전한 `(distanceSq, Id)` total order와 기존 output을 별도 검증해야 한다.
- atomic append, shared RNG, hash-container iteration을 사용하면 scheduler에 따라 결과가 달라진다.
- DOTS/Unity Physics 또는 custom movement로 전환하면 현재 collision 동작 동일성을 유지하기 어렵다.
- EditMode resolver 테스트만으로 movement, spawn, RNG, Physics, commit 및 이벤트 순서는 보호되지 않는다.

변경 파일은 없다. 지정 파일과 관련 설정·테스트를 읽기 전용으로 조사했으며, 현재 테스트 메서드 수가 Combat 26개·Recruit 6개임은 확인했지만 이번 설계 조사에서는 Unity Test Runner를 실행하지 않았다.
