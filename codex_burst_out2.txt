## 4. 결정성·게임플레이

전제 수정이 필요합니다. 현재 문서의 제품 계약은 전 플랫폼 cross-run bit-identical이 아니라 “같은 초기 상태와 step 입력에 대한 kernel 결과”이며 cross-run replay claim을 배제합니다([DESIGN.md:66](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Docs/CrowdCity/DESIGN.md:66>)).

Oracle은 raw float 위치와 team을 기록해 파일 바이트를 비교하지만([CrowdOracleHarness.cs:209](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Game/Editor/CrowdOracleHarness.cs:209>), [CrowdOracleHarness.cs:271](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Game/Editor/CrowdOracleHarness.cs:271>)), 기본 범위가 100/300/500/800이고 동일성 재실행은 첫 조합뿐입니다([CrowdOracleHarness.cs:40](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Game/Editor/CrowdOracleHarness.cs:40>), [CrowdOracleHarness.cs:118](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Game/Editor/CrowdOracleHarness.cs:118>)). 실제 SDF-ON prefab과 달리 하네스는 `AddComponent<CrowdRoot>`의 SDF-OFF 기본 경로입니다([CrowdOracleHarness.cs:143](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Game/Editor/CrowdOracleHarness.cs:143>), [CrowdRoot.prefab:47](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Crowd/Resources/Crowd/CrowdRoot.prefab:47>)).

규칙의 논리적 결정성은 유지 가능합니다. Recruit는 `(거리², claimant ID)`, combat은 team ID와 `(거리², agent ID)` 전순서를 사용합니다([RecruitResolver.cs:99](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Crowd/Core/RecruitResolver.cs:99>), [CombatResolver.cs:349](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Crowd/Core/CombatResolver.cs:349>), [CombatResolver.cs:545](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Crowd/Core/CombatResolver.cs:545>)). 폭발 원인은 tie-break 규칙이 아니라 insertion sort 구현입니다.

권장 계약은 다음입니다.

- stable ID와 canonical logical outcome 결정성 유지
- cell/agent ID 결정적 정렬
- `(tick, agentId, purpose)` counter-based RNG
- 위치는 fixed-point/quantized hash 또는 tolerance 비교
- GPU crowd는 authoritative combat과 분리
- 기존 raw-float oracle은 소규모 CPU reference fixture로 유지

- Combat victim insertion sort: pair당 최악 Θ(V²)([CombatResolver.cs:399](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Crowd/Core/CombatResolver.cs:399>), [CombatResolver.cs:545](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Crowd/Core/CombatResolver.cs:545>))

100k 하단은 native SoA, CSR/sort grid, 다단계 Burst jobs, O(1) membership, 결정적 radix/segmented 처리로 가능성을 시험할 수 있습니다. 500k full-fidelity에는 ECS/DOTS 또는 동급 custom data-oriented backend와 GPU 보조가 필요합니다. 단, ECS나 GPU도 고밀도 pair 수 자체의 Θ(N²)를 자동 해결하지는 않습니다.

## 4. 결정성·게임플레이

전제 수정이 필요합니다. 현재 문서의 제품 계약은 전 플랫폼 cross-run bit-identical이 아니라 “같은 초기 상태와 step 입력에 대한 kernel 결과”이며 cross-run replay claim을 배제합니다([DESIGN.md:66](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Docs/CrowdCity/DESIGN.md:66>)).

Oracle은 raw float 위치와 team을 기록해 파일 바이트를 비교하지만([CrowdOracleHarness.cs:209](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Game/Editor/CrowdOracleHarness.cs:209>), [CrowdOracleHarness.cs:271](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Game/Editor/CrowdOracleHarness.cs:271>)), 기본 범위가 100/300/500/800이고 동일성 재실행은 첫 조합뿐입니다([CrowdOracleHarness.cs:40](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Game/Editor/CrowdOracleHarness.cs:40>), [CrowdOracleHarness.cs:118](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Game/Editor/CrowdOracleHarness.cs:118>)). 실제 SDF-ON prefab과 달리 하네스는 `AddComponent<CrowdRoot>`의 SDF-OFF 기본 경로입니다([CrowdOracleHarness.cs:143](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Game/Editor/CrowdOracleHarness.cs:143>), [CrowdRoot.prefab:47](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Crowd/Resources/Crowd/CrowdRoot.prefab:47>)).

규칙의 논리적 결정성은 유지 가능합니다. Recruit는 `(거리², claimant ID)`, combat은 team ID와 `(거리², agent ID)` 전순서를 사용합니다([RecruitResolver.cs:99](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Crowd/Core/RecruitResolver.cs:99>), [CombatResolver.cs:349](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Crowd/Core/CombatResolver.cs:349>), [CombatResolver.cs:545](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Assets/@Project/Crowd/Core/CombatResolver.cs:545>)). 폭발 원인은 tie-break 규칙이 아니라 insertion sort 구현입니다.

권장 계약은 다음입니다.

- stable ID와 canonical logical outcome 결정성 유지
- cell/agent ID 결정적 정렬
- `(tick, agentId, purpose)` counter-based RNG
- 위치는 fixed-point/quantized hash 또는 tolerance 비교
- GPU crowd는 authoritative combat과 분리
- 기존 raw-float oracle은 소규모 CPU reference fixture로 유지

## 5. 현실적 로드맵

| 단계 | 핵심 변경 | 새 병목/게이트 |
|---|---|---|
| 2k 기준선 | 실제 SDF-ON prefab Player 빌드에서 spawn·memory·CPU/GPU·렌더 측정 | 현재 하네스는 800까지만, spawn/렌더 제외 |
| 2k→10k | state/view 분리, native SoA, stable ID, Human/CC는 근접 proxy만 | grid 후보 수, instance upload |
| 10k→50k | Burst multi-job, deterministic sort/CSR grid, insertion sort·managed List 제거, indirect+VAT | 메모리 대역폭, cell hotspot, GPU fill |
| 50k→100k | ECS/DOTS chunk 또는 동급 native scheduler, 필요 시 steering/SDF compute | CPU↔GPU 동기화·readback |
| 100k→500k | ECS+GPU hybrid/GPU-sim, spatial partition, multi-rate·simulation LOD | 모든 개체 50Hz exact combat 요구 자체 |

아키텍처상 `CrowdRoot`가 backend 생성·해제·규칙 owner로 남고 `GameplayRoot`가 wiring하는 구조는 유지할 수 있습니다([CLAUDE.md:104](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/CLAUDE.md:104>)). 그러나 “모든 agent가 Human prefab+enabled CC” 계약은 data-agent/proxy 모델과 직접 충돌하므로([PREFAB_CONSTRUCTION_PLAN.md:77](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/Docs/CrowdCity/PREFAB_CONSTRUCTION_PLAN.md:77>)), 구현 전 명시적 supersession과 Decision Log가 필요합니다([CLAUDE.md:88](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/CLAUDE.md:88>)).

MVP/Growth/Advanced는 개체수 등급이 아니라 연결 복잡도와 라이브 운영 단계입니다([CLAUDE.md:55](<D:/UNITY/UNITY_PROJECT/ActionFitPro/AF_CrowdCity/CLAUDE.md:55>)). 이번 요구는 data-oriented backend 도입을 정당화하지만 EventBus, RuntimeRegistry, Remote Addressables 같은 무관한 Advanced 구조 도입 근거는 아닙니다.

## 6. 최종 권고

**C — ECS/DOTS 또는 GPU-sim 중심 전면 재설계.**

100k 하단은 B vertical slice로 판정할 수 있지만, 100k~500k 전체 목표는 per-agent Unity 객체, 개별 렌더링, 고밀도 후보 열거와 명시적 Θ(N²) 경로를 제거하는 backend/view 전면 재설계가 필요합니다.

## 합의 후보

- 현재 1 agent = 1 Human GO/Transform/Animator/SMR/CC 구조는 100k에서 성립하지 않는다.
- 렌더링은 독립 병목이며 indirect instancing과 GPU animation, visual LOD가 필요하다.
- 단일 `IJobParallelFor` Burst화만으로는 managed 자료구조와 이차 알고리즘을 해결하지 못한다.
- 전순서 gameplay 결정성은 보존 가능하지만 raw-float bit equality는 대규모 병렬/GPU 계약으로 부적합하다.
- 100k는 B형 POC로 게이트할 수 있으나 500k full-gameplay 목표의 계획 기준은 C다.
- 현재 2,000은 설정값일 뿐, SDF·spawn·렌더를 포함한 검증된 성능 기준이 아니다.

변경 파일은 없습니다. 조사는 `rg`와 원본 파일 교차검증으로 수행했으며, 타깃 기기 Player Profiler·Memory Profiler·Frame Debugger 실측은 없어 절대 FPS/메모리 상한은 확인 불가입니다.
