## 1. 이 문서의 규칙

기능 영역별로 **변경 이력 한 쌍**(`CHANGELOG.en.md` + `CHANGELOG.ko.md`)을 둡니다.

| 항목 | 규칙 |
|---|---|
| 기록 시점 | **기능을 추가하거나 변경한 모든 커밋.** 성능(perf)·수정(fix)·툴링(tooling) 커밋 포함 |

## 2. 현재 상태와 다음 단계

### 2.1 완료된 것

| 항목 | 커밋 | 상태 |
|---|---|---|
| §2 분리 계측 — 프로파일러 세그먼트 7개 추가 | `1485848` | 반영 완료, 오라클 바이트 동일 |
| 에디트 모드 rig 유령 수정 — 지연 `Destroy` 직전 `SetActive(false)` | `dcb3bfb` | 반영 완료, 스크린샷 검증 |
| T1a — GPU 경로의 죽은 `transform.rotation` 쓰기 제거 | `fdf909d` | 반영 완료, 정확성 + 성능 실측 |
| §2 측정 증거 기록 + 계획 정정 | `ff60d39` | 반영 완료(문서만) |

**실측이 끝난 것은 두 가지**입니다. ①§2의 "직렬 vs 잡 대기" 분리(헤드리스, `CrowdProfileHarness`), ②T1a의 GPU 경로 이득(플레이 모드, `CrowdPerfHarnessP95`).

### 2.2 다음 작업 — 새 작업이 아니라 "재결정"이다

`SIM_OPT_10K_PLAN.md` §4는 지금 "다음 = T1b"라고 적혀 있습니다. **그 판정이 흔들렸습니다. T1b를 시작하기 전에 먼저 정리해야 합니다.**

이유를 순서대로 보면:

1. §2 측정은 **헤드리스**로 돌렸습니다. 헤드리스에서는 그래픽 디바이스가 없어 `CrowdRenderer.Init`이 `false`를 반환하고(`CrowdRenderer.cs:98`~`:102`) `_gpuRenderActive == false`가 됩니다. 즉 **SMR 경로**입니다.
2. 그래서 §2의 `*Present` 수치는 **T1a가 방금 제거한 그 쓰기까지 포함**한 값입니다. 계획 문서도 이 점을 "`*Present`는 상한(upper bound)"이라고 명시했고, 손익분기점을 숫자로 못 박아 뒀습니다 — 10k에서 **`Present` 비용의 86.1% 초과**가 SMR 전용이어야 판정이 뒤집힌다(`SIM_OPT_10K_PLAN.md` §2).
3. 그런데 T1a의 실측 이득은 **−12.83 ms/tick**입니다. 이는 10k의 `Present` 합계 13.58 ms(`FollowerPresent` 8.87 + `NeutralPresent` 4.71)의 **약 94%** 입니다.
4. 즉 문서가 "비현실적"이라고 판단했던 86.1% 선을, 다른 측정이 넘어 버렸습니다.

**그래서 해야 할 일:** T1b에 착수하기 전에 **GPU 경로를 켠 상태로 세그먼트를 다시 재는 것**. 구체적으로 `CrowdProfileHarness`를 **`-nographics` 없이** 실행해서 `CrowdRenderer.Init`(`CrowdRenderer.cs:64`)이 성공하고 `_gpuRenderActive`(`CrowdRoot.cs:119`, 설정 지점 `CrowdRoot.cs:888`)가 true인 상태의 수치를 얻어야 합니다.

> **반드시 함께 적을 유보 조건.** 두 수치는 **서로 다른 하네스, 서로 다른 모드**에서 나왔습니다 — 헤드리스 에디트 모드 `CrowdProfileHarness` vs 플레이 모드 `CrowdPerfHarnessP95`. 그래서 이것은 **해소해야 할 긴장(tension)** 이지, T1b가 틀렸다는 **증명이 아닙니다.** 같은 조건으로 다시 재기 전에는 어느 쪽도 결론이 아닙니다.

### 2.3 깨면 안 되는 불변식

| 불변식 | 위치 | 이유 |
|---|---|---|

### 2.4 함정

- **GPU 경로에서 팔로워/뉴트럴의 `transform.rotation`은 이제 영구히 stale**입니다. 이미 stale이던 위치에 회전이 합류한 상태입니다(기존 주석 `CrowdRoot.cs:740`이 "버려진 트랜스폼/CharacterController" 상태를 설명합니다). 앞으로 팔로워·뉴트럴의 `transform.rotation`이나 `.forward`를 읽는 기능을 추가하면 **조용히 스폰 시점 값**을 받습니다.
- **`fdf909d`(T1a)는 `dcb3bfb`와 결합되어 있습니다.** 되돌릴 때는 함께 되돌려야 합니다. 이유는 [5.5](#5-fdf909d-t1a-죽은-회전-쓰기-제거)에 있습니다.
- **Unity는 에디트 모드에서 지연 `Object.Destroy`를 거부합니다.** 이 프로젝트의 모든 에디트 모드 하네스(`CrowdShotHarness`, `CrowdProfileHarness`, `CrowdOracleHarness`)는 런타임 코드가 "파괴했다"고 믿는 객체를 계속 보게 됩니다. 덧붙여 `GetComponentsInChildren<SkinnedMeshRenderer>(true)`는 비활성 객체까지 세므로 에디트 모드에서 `smr == 0` 단언은 여전히 실패합니다. 플레이 모드 성능 하네스는 프레임마다 yield하므로 영향이 없습니다.
- **`CrowdPerfHarnessP95`의 CSV 열 `simtick_median_ms`는 중앙값이 아닙니다.** `CrowdPerfHarnessP95.cs:413`이 `totalSimMs / totalSteps`를 계산합니다 — 0.02초 스텝당 **산술 평균**입니다. 반면 `full_*`, `render_median`, `mainthread_*`는 진짜 백분위/최댓값입니다. 이 열 이름 하나 때문에 리포트를 잘못 읽기 쉽습니다.

## 3. 공통 컨벤션과 검증 게이트

### 3.1 시뮬 변경 — 오라클 바이트 동일 게이트

`CrowdOracleHarness`, **n=2000 · seed=12345 · 1000틱**, 스냅샷 md5 = **`4F79282EB20A79023B45F2EB2DE5271B`**.

시뮬레이션 결과가 바뀌지 않아야 하는 변경(메커니즘만 바꾸는 최적화)은 이 md5가 **바이트 동일**해야 통과입니다. events/summary CSV도 함께 비교합니다.

> ⚠️ **`SIM_OPT_HANDOFF.md:25`에 적힌 `2b3aad7f786004f1185a067bc1b31f4a`는 Burst 도입 이전의 낡은 기준선입니다.** 그 값으로 게이트하면 안 됩니다. Burst 산출은 Mono 오라클과 bit-identical하지 않기 때문에 재기준선이 있었고, 현재 유효한 값은 위의 `4F79282E…` 하나입니다.

### 3.2 렌더 변경 — 픽셀 허용오차 게이트 (MD5 금지)

| 항목 | 값 |
|---|---|
| 통과 기준 | **차이 ≤100 픽셀 AND 최대 채널 델타 ≤8** + 육안 확인 |
| 측정된 노이즈 플로어 | 동일 인자 재실행 간 이미지당 **921,600픽셀 중 3~16픽셀** 차이, 최대 채널 델타 ≤4 |
| 측정된 실제 변경 신호 | **35,587~123,161픽셀**, 최대 델타 **171~184** |
| 분리도 | 픽셀 수 약 **2,200배**, 최대 델타 약 **43배** |

노이즈는 시뮬이 아니라 **렌더 단계**에서 옵니다 — 같은 실행에서 오라클 스냅샷은 bit-stable로 증명됐고, **손대지 않은 `smr_off.png`까지** 3픽셀 달라졌습니다. 자세한 경위는 [6.8절](#6-dcb3bfb-에디트-모드-rig-유령-수정)에 있습니다.

### 3.3 커밋 위생 — TMP 에셋 부수 효과

헤드리스 Unity 하네스를 한 번 돌릴 때마다 `Assets/TextMesh Pro/Resources/Fonts & Materials/LiberationSans SDF - Fallback.asset`이 더럽혀집니다(대략 10 insertions / 911 deletions). Unity 쪽 부수 효과이며 의미 있는 변경이 아닙니다.

- 커밋 전에 **되돌리세요.**
- **`git add -A`를 절대 쓰지 마세요.** 항상 경로를 명시해서 스테이징합니다.

### 3.4 타이밍 측정 — 조용한 머신

측정 직전에 호스트 전체 CPU 사용률을 읽고, **약 30%를 넘으면 미루세요.**

이 임계값은 관측에서 나왔습니다. 포그라운드 게임이 코어 하나를 온전히 점유한 상태(배경 부하 총합 약 3.16 코어)에서 측정했을 때 **병렬 구간은 +66%** 부풀었지만 **직렬 구간은 +8~13%** 만 움직였습니다. 즉 배경 부하는 오염을 **균등하게 주지 않고 병렬 구간에 집중**시킵니다. "직렬 vs 병렬" 중 어느 쪽이 큰지를 가르는 측정에서는 이 편향이 곧 잘못된 판정이 됩니다.

### 3.5 성능 목표 수치를 지어내지 않는다

프로젝트 규칙입니다(`SIM_OPT_HANDOFF.md` §7 "성능 목표 수치 지어내기 금지").

- 게이트는 "**런 간 spread를 넘는 개선**"으로 서술합니다.
- 차이가 spread 안에 들어가면 **"판정 불가(inconclusive)"** 로 보고합니다. "효과 없음"도, "효과 있음"도 아닙니다.

## 4. ff60d39 측정 증거와 계획 정정

`[Docs]` · `Docs/CrowdCity/Perf/simopt10k_step1_r{1,2,3}.txt` + `Docs/CrowdCity/Perf/MANIFEST.md` 신설, `SIM_OPT_10K_PLAN.md` §2·§4 재작성. **코드·빌드·런타임 표면 변경 없음.**

### 4.1 이 측정이 답하려 한 질문

10k 최적화의 다음 단계가 **T1b**(직렬 제시 패스를 잡으로 옮기기)인가 **T2**(잡이 하는 일 자체를 줄이기)인가. 두 후보는 서로 다른 곳을 손대므로, 먼저 `FollowerSteer`/`NeutralMove`를 "메인스레드 직렬"과 "잡 벽시계 대기"로 쪼개 봐야 했습니다.

### 4.2 측정 설계

| 항목 | 값 |
|---|---|
| 하네스 | `CrowdProfileHarness` (에디트 모드 헤드리스, `-batchmode -nographics`) |
| 솔버 | SDF ON 강제 + `IsSdfActive` 단언 + `CcMoveFallbacks == 0` 단언 |
| 시드/스케일 | seed=12345, neutralCount 5000 / 10000 (agents 5004 / 10004) |
| 스케일당 틱 | sdfVerify 20 + warmup 200 + timing 1000 + gc 500 |
| 런 수 | 3 (인자 동일, 라벨/출력 경로만 다름) |
| 호스트 | Ryzen 5 5600X (6C/12T), Windows 10 Pro, Unity 6000.3.9f1 |

**`-profileCounters`는 일부러 전달하지 않았습니다.** work counter는 타이밍을 교란하고, 하네스가 counter를 별도 pass로 분리해 둔 이유가 바로 그것입니다. 이번 질문은 타이밍 분리이므로 counter는 불필요하고, 켰다면 판정 대상 수치를 오염시켰을 것입니다.

**판정 규칙은 측정 전에 고정했습니다.**

- T1b 대상(직렬) = `FollowerPrepass` + `FollowerGridSnapshot` + `FollowerPresent` + `NeutralPrepass` + `NeutralPresent`
- T2 대상(잡 벽시계) = `FollowerJobWait` + `NeutralJobWait`
- spread(노이즈 대역) = 두 합 각각의 (max − min)을 **더한** 값 — 보수적으로 잡았습니다
- **차이가 spread를 넘지 못하면 판정 불가** → 재측정하거나 런을 늘린다

측정 후에 규칙을 만들면 원하는 결론이 나오게 규칙을 고를 수 있습니다. 그래서 순서를 뒤집지 않았습니다.

### 4.3 결과

| 스케일 | T1b 대상(직렬) | T2 대상(잡 대기) | Total | 차이 / spread |
|---|---|---|---|---|
| 5000 | **4.39 ms (68.3%)** | 0.52 ms (8.1%) | 6.43 ms | 3.87 / 0.079 = **49배** |
| 10000 | **14.47 ms (70.4%)** | 2.78 ms (13.5%) | 20.56 ms | 11.69 / 0.197 = **59배** |

세 가지가 따라 나옵니다.

### 4.4 계획의 산식이 틀렸던 이유 — 명시적 정정

`SIM_OPT_10K_PLAN.md` §2 초판은 직렬 비용을 이렇게 구하자고 적었습니다.

```
직렬 = FollowerSteer − CCMove − (.Complete 대기)
```

**이 산식은 성립하지 않습니다.** 두 가지가 동시에 깨집니다.

1. **`Seg.CCMove`는 특정 분기의 몫이 아니라 다섯 지점을 합산하는 단일 버킷**입니다.

   | 지점 | 위치 |
   |---|---|
   | 리더 `ApplyHorizontalMove` | `CrowdRoot.cs:1185` |
   | 팔로워 SDF 이동 잡 대기 | `CrowdRoot.cs:1390` |
   | 팔로워 CC 폴백 | `CrowdRoot.cs:1479` |
   | 뉴트럴 SDF 이동 잡 대기 | `CrowdRoot.cs:1608` |
   | 뉴트럴 CC 폴백 | `CrowdRoot.cs:1657` |

   즉 공개된 `CCMove` 값에는 팔로워와 뉴트럴의 대기가 섞여 있어, `FollowerSteer`에서 `CCMove` 전체를 빼는 것은 팔로워가 쓰지 않은 비용까지 빼는 일입니다.

2. **`*JobWait`은 `CCMove` 안에 중첩**되어 있습니다. `CCMove`를 이미 뺀 뒤 `.Complete()` 대기를 또 빼면 **같은 구간을 두 번 차감**합니다.

그래서 산식으로 유도하는 대신, `1485848`에서 **분기별 세그먼트를 직접 넣어 계측**했습니다. 이 정정을 계획 문서 본문에 남긴 이유는, 산식이 그럴듯해 보여서 다음 사람이 같은 실수를 반복할 가능성이 높기 때문입니다.

### 4.5 부하 통제 — r2를 왜 버리지 않았나

3.4절의 30% 규칙을 적용하면 세 런 모두 채택입니다. 다만 **r2만 ambient 19.4%** 로, r1(8.7%)·r3(8.3%)의 약 **2.3배** 부하에서 돌았습니다. 병렬 구간이 부하에 민감하다는 것을 이미 알고 있었으므로, 그냥 넘기지 않고 **잡 대기가 계통적으로 부풀었는지** 확인했습니다.

- `FollowerJobWait`@10k — r1 2.6809 / **r2 2.6650** / r3 2.6410 → r2는 최댓값이 아니라 **3개 중 중간값**입니다.
- `FollowerJobWait`@5k — r1 0.4223 / r2 0.4224 / **r3 0.4377** → **최저 부하 런(r3, 8.3%)이 오히려 최댓값**입니다.

즉 이 부하 범위(≤19.4%)에서는 병렬 구간 오염이 관측되지 않습니다. 이것은 3.4절의 대조 사례와 뚜렷하게 다릅니다 — 코어 하나가 점유된 상태에서 폐기했던 이전 시도에서는 병렬 구간 **+66%** vs 직렬 구간 **+8~13%** 로 갈렸습니다. 30% 임계는 그 관측에서 온 값이고, r2는 그 아래이며 실제로도 편향이 보이지 않았습니다.

### 4.6 알려진 측정 공백 2건

둘 다 `Perf/MANIFEST.md` §6에 명시했습니다. **숨기지 않고 적는 것이 핵심**입니다 — 아래 ①은 4.3절 결론 3의 근거를 약화시키기 때문입니다.

1. **팔로워/뉴트럴 모집단 수가 출력되지 않습니다.** 하네스는 내부적으로 추적하지만 출력 파일에 쓰지 않습니다. 그래서 "팔로워 계열 6~10배 vs 뉴트럴 계열 1.06~1.69배"라는 비대칭의 원인을 **모집단 구성 이동(population-mix shift)으로 추론**할 뿐 **측정하지 못했습니다.** 세그먼트당 비용이 정말 나빠졌는지, 아니면 단순히 팔로워 수가 훨씬 많이 늘어난 것인지 이 데이터로는 가릴 수 없습니다.
2. **`RenderInterpolate`는 이 측정 범위 밖입니다.** 하네스는 `SimTick`만 돌리고 `RenderInterpolate`를 호출하지 않으므로, 거기의 per-agent transform 쓰기(`CrowdRoot.cs:747`, `:755`)는 위 어떤 수치에도 포함되지 않습니다.

### 5.2 왜 이 쓰기가 죽은 코드인가

`Human.SetHeadingAndSpeed`는 두 가지를 합니다(`Human.cs:87`~`:95`).

```csharp
transform.rotation = Quaternion.Euler(0f, headingDeg, 0f);   // Human.cs:89
if (_animator != null) { _animator.speed = ...; }             // Human.cs:91
```

GPU 크라우드 렌더러가 활성이면:

- yaw는 `_visualYaw`에서 읽습니다 (`CrowdRoot.cs:914`)
- 애니메이션 위상은 `_visualSpeed01` / `_phase01`에서 적분합니다 (`CrowdRoot.cs:909`)
- 비주얼 rig는 파괴·비활성화되어 있습니다 (`dcb3bfb` 이후)

즉 **이 쓰기의 소비자가 없습니다.** 결과가 어디에도 반영되지 않는 네이티브 쓰기이며, 1만 규모에서 **틱당 약 1만 회** 발생했습니다.

### 5.3 왜 `Human`이 아니라 호출부에서 게이팅했나

두 가지 설계 이유가 겹칩니다.

1. **`_gpuRenderActive`는 `CrowdRoot`의 private 필드**입니다(`CrowdRoot.cs:119`). 이걸 `Human`이 알게 하려면 노출하거나 주입해야 합니다.
2. **`Human`은 설계상 완전 수동형 leaf**입니다. 렌더 모드를 판단하는 지식을 leaf에 내려보내면, leaf가 상위의 렌더 전략을 알게 되어 프로젝트의 소유권 규칙(CLAUDE.md §2)이 무너집니다.

그리고 이미 같은 패턴의 선례가 있습니다 — **S4b2의 caller-side 위치 게이트**(`CrowdRoot.cs:747`, `:755`)가 정확히 같은 방식으로 `transform.position` 쓰기를 호출부에서 막습니다. 새 패턴을 만든 것이 아니라 기존 패턴을 재사용했습니다.

### 5.9 왜 정직한 헤드라인은 −12.83 ms인가

`full_median`이 115.3 → 17.9 ms이므로 "프레임이 7배 빨라졌다"고 쓰고 싶어집니다. **쓰면 안 됩니다.**

약 97 ms의 프레임 격차는 **캐치업 누산기(accumulator) 포화** 때문에 증폭된 값입니다.

- 하네스의 시뮬 케이던스는 `MaxStepsPerFrame × FixedStep` = **4 × 20 ms = 80 ms**입니다 (`CrowdPerfHarnessP95.cs:164`, `:165`).
- BEFORE의 프레임 주기 115 ms는 이 80 ms를 **초과**합니다 → 누산기가 매 프레임 4틱 상한에 붙습니다.
- 실제로 `ticksPerFrame`이 BEFORE **3.994** vs AFTER **0.912**입니다. BEFORE는 프레임마다 시뮬을 4번 돌리고, AFTER는 1번도 채 돌리지 않습니다.

산술로 확인됩니다.

```
3.994 × 23.113  −  0.912 × 10.287  =  82.9 ms   (시뮬 몫)
82.9 + 14.9(렌더)                   =  97.8 ms
실측 격차                            =  97.4 ms   ✅
```

즉 프레임 격차의 대부분은 "틱당 비용 절감 × 틱 수 증폭"입니다. **틱당 −12.83 ms가 실체이고, 97 ms는 그 실체가 상한에 걸린 구성에서 증폭된 결과**입니다. 이 구분을 흐리면 다른 구성(예: 프레임 주기가 80 ms 아래인 환경)에서 기대치가 어긋납니다.

### 5.10 메커니즘 — 왜 제거된 호출 하나가 1.28 µs인가

12.83 ms를 약 1만 회로 나누면 호출당 **약 1.28 µs**입니다. 단순한 `transform.rotation` 쓰기 하나에는 **너무 큰 값**이고, 이 불일치를 설명하지 못하면 측정을 신뢰할 수 없습니다.

설명은 `Human.SetHeadingAndSpeed`의 **두 번째 줄**에 있습니다.

```csharp
if (_animator != null)   // Human.cs:91
```

GPU 경로에서 `_animator`는 **파괴된 `UnityEngine.Object`** 를 참조합니다. Unity에서 `UnityEngine.Object`의 `!= null` 비교는 순수 C# 참조 비교가 아니라 **네이티브 alive-check ICall**로 내려갑니다. 즉 게이팅으로 제거된 것은 "회전 쓰기 하나"가 아니라 **회전 쓰기 + 네이티브 왕복 비교**이고, 10k 에이전트에서는 틱당 약 1만 번입니다.

이 비용은 이 프로젝트가 **이미 별도로 기록해 둔 상위 병목**입니다 — 이전 에디터 프로파일러 캡처에서 `Loading.IsObjectAvailable`이 3004 에이전트에 대해 프레임당 **6008회**(= 2 × 3004) 잡혔습니다. 같은 종류의 비용이 여기서 다시 나온 것이므로, 1.28 µs/호출은 이상치가 아니라 **일관된 관측**입니다.

2. CC 분기에서는 이동과 제시가 **물리적으로 뒤섞여** 있어 직렬/병렬로 쪼갤 수 없습니다. 쪼개려면 코드 구조를 바꿔야 하고, 그건 계측이 아니라 리팩토링입니다.

**8번째 세그먼트 `NeutralRepick` — 기각**

이벤트 단위(per-event) 계측을 추가하자는 안이 있었으나 **투기적 계측(speculative instrumentation)** 으로 판단해 넣지 않았습니다. 답해야 할 질문(직렬 vs 잡)에 필요하지 않고, 계측 지점이 늘어날수록 오버헤드와 판독 복잡도가 함께 늘어납니다. 필요해지면 그때 추가합니다.

**`CrowdProfileHarness` — 무수정**

하네스는 `Seg.Count`로 열거하고 `Accum.Length`(`CrowdSimProfiler.cs:54`)로 배열 크기를 잡으므로, 코드를 고치지 않고도 SEGMENTS 표가 스케일당 **12행 → 19행**으로 자동 확장됩니다. 열거형을 확장 가능하게 설계해 둔 덕을 본 지점입니다.
